# DAEX Implementation Roadmap

This document outlines the strategic phases for evolving DAEX from a simple LLM wrapper into an autonomous on-device AI engine.


## Feature Improvements (2026-07-12 review)
**Goal:** Beta hardening is done. These make the assistant itself smarter and more capable, independent of the UI it's presented through.

- [x] **Layered system prompt (persona + custom instructions)**: today, setting a custom system prompt (`SettingsScreen.kt`) fully *replaces* the default identity block in `DaexService.kt` — a user who adds "always answer in bullet points" silently loses the anti-self-reference and timestamp-handling instructions too, and can end up with a model that breaks character or mishandles voice timestamps without realizing why. Split into a fixed base persona layer plus an appended user-instructions layer, so custom prompts extend rather than overwrite. Shipped as an always-on base persona (name self-reference now allowed) with tool-awareness and custom instructions layered on top as short, clearly-delimited sections — kept deliberately compact given the shared 4096-token budget on-device. Verified on-device: asking "who are you" now gets a natural "I am Icarus..." instead of an evasive non-answer.
- [x] **Cold-start suggested prompts**: `generateSuggestedPrompts()` is genuinely contextual — it asks the model for starters based on the last 15 turns — but on a brand-new conversation there's no history to draw from, so the very first suggestions a user ever sees are generic. Seed the first-ever set from the model/hardware picked during onboarding and the "showcase" capability the user seemed most interested in (RAG vs. tools vs. voice), instead of an empty-history fallback prompt. Reworked after discussion: onboarding-tap/app-state signals don't map cleanly onto real prompt text, so instead a bundled `about_daex.md` system document (hidden from the user-facing document list) is ingested through the real RAG pipeline once, and cold start seeds from a fixed pool of questions about DAEX's own capabilities. Found via a real fresh-install test (full app data clear) that grounding silently failed: the embedding model's background download was skipped entirely for the whole first session, since it shared the chat model's single generative-download slot and explicitly deferred to "next launch" whenever that slot was busy — which is always true during onboarding, the exact moment this feature needs it. Fixed properly (not just papered over) by giving the embedding model its own independent download lane in `ModelManager`/`ModelDownloadService`/`ModelDownloadState` (mirroring the existing Kokoro TTS lane), so it downloads *concurrently* with the mandatory chat model download instead of waiting on it at all; re-seeds the suggested prompts once ingestion completes. Verified on-device (without a full model re-download) by deleting just the embedding model file and confirming the new independent `ACTION_DOWNLOAD_EMBEDDING` lane re-downloads and re-initializes it cleanly. Not yet re-verified with a full fresh-install onboarding run (would require re-downloading the multi-GB chat model, so left for the user to re-trigger if they want to see true concurrency in action).

Separately, once retrieval was actually firing reliably, a real fresh-install test still surfaced thin answers ("a small hint it's entirely unsure about") — `about_daex.md` itself was too sparse (7 short sections, ~1.7K characters) to answer most questions in real detail. Rewrote it into a genuinely comprehensive reference (12 sections, ~6.3K characters covering models, RAG, cross-conversation search, tool calling, voice mode, read-aloud, memory, saved prompts, personalization, and privacy in real detail), and added content-version tracking (`ABOUT_DAEX_CONTENT_VERSION`) so devices that already ingested the old thin version clear it and re-ingest the new one automatically rather than silently keeping stale content forever. Verified on-device: re-ingestion correctly deleted the old 10 chunks and ingested 30 new ones, and a live query ("Do you remember things between conversations?") retrieved the exactly-relevant section (score 0.018, best match out of 30) and produced an accurate, confidently-grounded answer instead of a hedge.
- [x] **Tool-aware system prompt**: available tools are passed to the engine structurally (`ConversationConfig.tools`), but the model is never told in prose what it can currently do. On models/configs where structural tool-calling is flaky, a short "you have access to: battery status, file search, ..." line in the system prompt would make tool use more reliable and let the model explain its own capabilities when asked. Shipped as a one-line capability summary (`ToolRegistry.capabilitySummary()`), appended only when tool calling is enabled and reflecting only the tools currently enabled (see per-tool enable/disable below). Verified on-device: asking "what tools do you have" correctly lists the enabled device tools.
- [x] **Cross-conversation search**: FTS5/BM25 hybrid search already exists for RAG documents, but there's no way to search across *past conversations* — only the currently-open thread is visible. Reuse the existing FTS infrastructure to index message content and add a search entry point from the Sidebar. Shipped as a hybrid vector+BM25 search (`DaexMemory.searchMessages`, new `DaexMessageFtsHelper`) with a one-time background backfill for pre-existing messages, an inline search field in `Sidebar.kt`, and a separate agentic `RecallMemoryTool` the model can call on its own — deliberately *not* auto-injected into every turn, to avoid pulling unrelated history into context. Verified on-device: searching surfaced the right past conversation and tapping it opened correctly; the message backfill ran successfully on 23 pre-existing messages.
- [x] **Saved prompt library**: suggested prompts are one-shot and disappear once the chat starts. Let users pin a suggestion (or any past message) into a personal reusable prompt library, surfaced as an alternative to the "starter prompts" empty-state. Shipped reusing the existing `Message.isPinned`/`MessageEntity.isPinned` column (previously dead), a pin toggle on both user and model message bubbles, and a new `SavedPromptLibraryModal.kt`. Verified on-device: pinning, viewing in the library, and tapping to start a new auto-submitted conversation all work.
- [x] **Per-tool enable/disable**: "Native Tool Calling" is currently one global switch. As the tool registry grows (Phase 4), expose which individual tools are available per-conversation — useful for privacy (e.g. disable location/contacts tools by default) and for reducing prompt-injection surface from tool descriptions the model doesn't need. Shipped as a global (not per-conversation) setting: `DeviceTools` split into one `ToolSet` class per tool (`DeviceToolSets.kt`), a `ToolRegistry` with per-tool defaults, and a nested toggle list in Settings under the existing master switch. Higher-risk tools (launch apps, send email, run system intents, recall past conversations) default off; read-only tools default on. Verified on-device: all 9 tools render with the correct default on/off state.
- [x] **Memory curation transparency**: global core memory is auto-curated in the background (`compactMemory`), but the user only sees a transient "[SYSTEM_LOG]: GLOBAL MEMORY CURATED" line. Surface a lightweight diff/summary ("learned: you prefer active-recall study techniques") so curation feels like a visible feature instead of an invisible background process the user has to trust blindly. Shipped via a plain Kotlin bullet-diff (no extra model call) in `DaexCoreMemory.compactMemory`, falling back to the generic message when nothing new surfaces. Verified on-device both ways: the diff line and the unchanged fallback.
- [x] **Per message read aloud button**: currently, voice read-aloud only works during live voice sessions. It would be nice to allow the user to read aloud any message in the chat by tapping a button on the message bubble. Shipped as a per-message "LISTEN"/"STOP" toggle in `MessageLine.kt`, reusing the existing `KokoroTtsService` pipeline. Verified on-device: play and stop both work correctly.

## UI/UX Improvements (2026-07-12 review)
**Goal:** The app has real motion polish *within* screens (message bubbles, modals, the send/mic morph button) but rougher edges at the seams — screen-to-screen navigation, first-run education, and empty states.

- [ ] **Screen transition animation**: `MainActivity`'s top-level `when (screen)` swap between Landing/Execution/Gallery/Settings is an instant cut with no `AnimatedContent`/`Crossfade` — jarring compared to the polish already present inside each screen. Wrap it in a shared transition (slide + fade matches the existing modal/card motion language) for a more cohesive feel with minimal risk, since it only touches the outer navigation shell.
- [ ] **Voice mode onboarding slide**: the 6-page onboarding walks through privacy philosophy, hardware diagnostics, sandbox tools, core memory, and RAG — but never mentions live voice mode, despite it being a flagship feature (Kokoro TTS, live transcription, barge-in). Add a slide, or fold it into the existing `TutorialSlide` carousel alongside the think-tag/RAG/tool-call previews.
- [ ] **Skippable, revisitable onboarding**: onboarding is forward-only (`userScrollEnabled = false`, no back-swipe) and shown exactly once — there's no "skip for now" for returning/technical users, and no way to replay it later if a user wants a refresher after forgetting a feature exists. Add a skip affordance and a "Replay onboarding tour" entry in Settings (System tab, next to the existing changelog button).
- [ ] **Automatic "what's new" on update**: `ChangelogModal.kt` already parses `CHANGELOG.md` and renders it — but it's manual-only, tucked in Settings. Track last-seen version in `DaexPreferences` and auto-show the modal once after an app update, filtered to entries since that version, so shipped work actually gets seen instead of relying on users to go looking for it.
- [ ] **Empty-state pass**: the RAG document library has a real empty state ("No documents in library."), but the conversation Sidebar has none at all — a fresh install's history list just renders blank with no explanation or call-to-action. Add a consistent empty-state treatment (icon/illustration + short copy + action) across Sidebar, document library, and gallery, replacing the current plain-text-only approach.
- [ ] **Expanded theme customization**: the "THEME" settings tab offers 6 fixed accent colors (hardcoded list + a matching hardcoded light-mode remap `when`) and a dark/light switch — no custom color picker, no text-size/accessibility scaling. A basic HSV picker and a font-scale slider would meaningfully widen who the app is comfortable for, and pairs naturally with the accessibility pass already noted in P1.
- [ ] **Persona/instructions split in Settings UI**: pairs with the "layered system prompt" feature above — once the underlying prompt is split, give it two visually distinct fields in Settings ("Icarus's personality" vs. "your instructions") instead of one undifferentiated text box, so the UI communicates that custom instructions *add to* rather than *replace* the assistant's behavior.

## Phase 0: Public Beta Hardening (2026-07-11 review)
**Goal:** Fix the reliability gaps that will cost first-impression users, before feature work resumes. Ranked by impact.

### P0 — must fix before beta
- [x] **ObjectBox re-entry crash**: `BoxStore` was rebuilt in `MainActivity.onCreate` every time the activity was (re)created; reopening the app while the previous store was still open threw `DbException: Another BoxStore is still open`. Moved `BoxStore` to a `by lazy` singleton on `DaexApplication`, scoped to the process lifetime instead of the Activity lifetime. Verified via repeated force-stop + rapid double-launch (the exact repro from field logs) — zero crashes, conversation history/RAG reads correctly through the shared instance.
- [x] **Model download resilience** (`ModelManager.kt`): no HTTP Range resume, no `.part`-then-rename, and the "≥90% of expected size" check accepts truncated/corrupt files. A first-run is a 2.6–3.7GB download — any interruption currently means starting over, and a corrupt-but-"valid-enough" file fails opaquely at engine load. Add resume support, temp-file-then-atomic-rename, and exact-size or checksum validation.
- [x] **Foreground service for downloads** (`dataSync` type minimum): screen-off or app-switch during the mandatory first-run download currently kills it. Voice-session foreground service (`microphone` type) is a stretch goal for the same reason but more forgivable at beta.
- [x] **Crash visibility**: no crash reporting anywhere (reasonable given the privacy-first positioning), but there's also no local capture — wire an uncaught-exception handler into the existing `LogShareHelper.kt` so the app can offer "share crash log" on next launch. Otherwise beta feedback is unactionable ("it crashed").
- [x] **Storage check before download**: `ModelManager.checkSpecSupport` explicitly ignores free storage (`supported = hasEnoughRAM`) — a 3.7GB download onto a nearly-full device fails mid-write. Gate the download button on `hasEnoughStorage` too.
- [x] **Release build hygiene**: `versionCode` is hardcoded to `1`; decide the Play internal-testing-track vs. sideload-APK distribution path before beta (the former gets staged rollout + crash/ANR vitals for free — covers part of the crash-visibility gap above). Sideload via GitHub Releases confirmed as the distribution path.

### P1 — should fix early in beta, not necessarily before
- [ ] Voice UI latency feedback: no visible state during the ~4-5s first-sentence TTS synthesis or long prefill — same latency reads as "broken" without a "thinking…"/"voicing…" indicator.
- [x] Per-token O(n²) re-parsing in the streaming callback (`DaexInferenceViewModel.kt`) — re-scans full accumulated text and copies the full message list on every token; fine for short voice replies, will jank on long text generations on mid-range hardware. Fixed by throttling the parse+publish to ~30fps (StringBuilder accumulation, existing parser untouched) with a guaranteed-correct final flush; also fixed a pre-existing bug where the live-voice end-of-stream TTS flush indexed into the raw (tag-included) text using an index tracked against the tag-stripped text.
- [x] Full conversation/context rebuild every turn (`DaexService.kt`) — re-prefills entire history each turn; a meaningful chunk of voice-loop latency. Confirmed via direct inspection of the `litertlm-android` library's compiled classes that `Conversation.sendMessage*` supports continuing an existing session without resupplying history. Implemented conversation reuse scoped to live voice turns (text chat has more per-turn-varying state — RAG context, relative timestamps — left on the always-recreate path for now), gated on conversation id + sampler/reasoning/tool settings all matching, with an automatic one-time fallback to a fresh conversation if reuse fails before any token arrives. Verified live: turns 2+ in a voice session correctly reuse the conversation (confirmed via logs) and stay contextually coherent.
- [ ] Onboarding length: six slides plus a mandatory multi-GB download before first real use. Consider a skippable tutorial and starting the download in the background during it.
- [ ] Denied `RECORD_AUDIO` silently no-ops the voice button — needs a visible explanation/retry path.
- [ ] Accessibility pass: the custom `BasicText`-everywhere design system likely doesn't respect font scaling or TalkBack. One pass before beta widens the audience.
- [ ] README/ROADMAP drift: README still describes Room (app actually uses ObjectBox + FTS5/BM25 hybrid retrieval); Phases 2 and 4 below are substantially implemented in code but shown unchecked. Keep these docs in sync going forward — they're a first impression for technical users browsing the repo.
- [ ] Zero automated tests in the repo. Not a beta blocker, but the most fragile code (WAV writer, VAD gate state machine, download validation) is exactly where a regression would be silent and costly. Even minimal unit coverage on those three would pay for itself.

### Post-beta arcs (not urgent, tracked for later)
- **Voice v2**: clause-level splitting for faster first-sentence audio, thermal/battery monitoring during long sessions (LLM + Kokoro concurrently will heat mid-range phones), and interruption/barge-in done via proper software echo cancellation using the TTS reference signal already available in `KokoroTtsService` (makes barge-in tractable instead of threshold-tuning against device-specific echo).
- **Agentic depth** (Phases 3-4 below): tool registry already exists; intent router and structured-output constraints are the missing pieces.
- **Distribution & licensing**: verify Gemma weight redistribution terms from the `litert-community` HuggingFace mirror hold up at beta scale; confirm ObjectBox's AGPL terms are compatible with any future commercial path.
- **Full background execution & default-assistant role**: promote the whole inference pipeline (not just downloads) to survive backgrounding — prompt the model, leave the app, and it keeps generating; response delivery via notification (progress while generating, then either the completed response or a "response ready" notification), rather than today's silent orphaning of an Activity-scoped `DaexInferenceViewModel`/coroutine when the Activity is destroyed. Paired ambition: register DAEX for Android's Assist/Voice Interaction role (`VoiceInteractionService`) so it can be set as the device's default assistant instead of only being a standalone app. Substantially bigger than the download service above (a real background execution + notification-response architecture, plus an OS integration surface) — its own multi-phase arc, not a single foreground-service change.

## Phase 1: Persistence & Session Management (The Foundation)
**Goal:** Ensure the AI doesn't "forget" and can manage multiple distinct conversations.
- [x] **Room Database Integration:** Implement `Conversation` and `Message` entities.
- [x] **DaexMemory Service:** Create a repository-pattern service to handle DB operations.
- [x] **Chat Sessions:** UI updates to the Sidebar to support creating, switching, and deleting threads.
- [x] **Context Windowing:** Implement a sliding window logic to manage the 2048-token limit of the engine.

## Phase 2: RAG - Retrieval Augmented Generation (The Knowledge)
**Goal:** Allow the AI to access local data and long-term history via vector search.
- [ ] **Embedding Engine:** Set up a secondary `llama.cpp` context for text-to-vector transformation.
- [ ] **Vector Store:** Implement a local vector search (ObjectBox or custom float-array index).
- [ ] **Semantic Search:** Enable the AI to "search" through its own past conversations and local device data.

## Phase 3: Intent Routing & Decomposition (The Logic)
**Goal:** Make the app smart enough to plan its own execution.
- [ ] **BNF Grammar Support:** Force LLM output into structured JSON for reliability.
- [ ] **Intent Router:** A fast classification step to decide if a query is a chat, a tool-request, or a multi-part task.
- [ ] **Task Decomposition:** Logic to break "Check my battery and write a poem" into a sequence of sub-tasks.

## Phase 4: Agentic Loops (The Action)
**Goal:** Give the AI the ability to interact with the Android OS.
- [ ] **Tool Registry:** Define a standard interface for Kotlin functions the AI can trigger.
- [ ] **ReAct Loop:** The "Think-Act-Observe" cycle within the `DaexInferenceViewModel`.
- [ ] **Hardware Tools:** Implement tools for Battery, Storage, Connectivity, and System Settings.

## Phase 5: Optimization & Polish (The OS)
**Goal:** Performance at scale.
- [ ] **SLM Routing:** Use a <0.8B model for high-speed intent routing to save battery.
- [ ] **Foreground Service:** Allow the AI to complete long-running tasks in the background.
- [ ] **Hardware Acceleration:** Further optimization of Vulkan/GPU layers for modern mobile SoCs.
